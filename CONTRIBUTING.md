# Contributing to rules_tofu

## Development setup

Prerequisites:

- [Bazel](https://bazel.build/) at the version in
  [`.bazelversion`](.bazelversion)
  ([Bazelisk](https://github.com/bazelbuild/bazelisk) selects it automatically)
- A C toolchain (`rules_go` compiles Go binaries with cgo enabled)
- `git` on `PATH` (`tf_modules` runs the host `git` to fetch git sources)

Clone, build and test:

```sh
git clone https://github.com/benbirt/rules_tofu.git
cd rules_tofu
bazel build //...
bazel test //...
```

## Repository layout

| Path | Purpose |
|------|---------|
| `tf/` | Public rules (`tf_library`, `tf_deploy`, `tf_test`) |
| `tf/providers/` | `tf_providers` module extension |
| `tf/modules/` | `tf_modules` module extension |
| `tf/private/` | Rule implementations and work-tree materialisation |
| `tf/private/cmd/{runner,dupcheck,pin,lockjson,modscan,modules}/` | Go binaries: build-time validation and runtime `tofu` wrapper, duplicate-variable check, `@tf_providers//:pin`, lock reader, module scanner and module manifest writer |
| `tf/private/cmd/internal/{flags,tfconfig,tofushow}/` | Shared Go packages: repeatable CLI flags; file-set, module-source, provider-address and test-file helpers; and `tofu show -json -module` inspection (with `tofushow/tofutest` for Go tests) |
| `toolchain/` | OpenTofu binary download and toolchain registration |
| `tofu/` | `@rules_tofu//tofu`, the toolchain's runnable `tofu` (rule in `tf/private/tofu_binary.bzl`) |
| `docs/` | `starlark_doc_extract` target per public `.bzl` file, shipped as the BCR `docs_url` archive |
| `tools/` | Maintainer tools (excluded from releases): `update_versions` pins OpenTofu releases; `format` formats the repository; `lint` lints every Starlark file |
| `tests/integration/` | Bazel-in-Bazel integration tests ([`tests/integration/README.md`](tests/integration/README.md)) |
| `tests/tofu/` | Tests for `//tofu` used as another target's tool |
| `examples/` | Usage examples |
| `e2e/smoke/` | Standalone consumer module; BCR presubmit test module |
| `.bcr/` | Bazel Central Registry metadata, source and presubmit templates |

## Hard invariants

1. One lock file, owned by the root module. `rules_tofu` reads only the root
   module's `tf_providers.from_lock` `.terraform.lock.hcl`, written by
   `bazel run @tf_providers//:pin`. Do not accept `.terraform.lock.hcl` in
   `srcs` or `data`, and do not relax the analysis-time check in `materialize`
   (`tf/private/work_tree.bzl`) that rejects it in any work-tree directory.
   Providers on `registry.opentofu.org` are pinned by that lock alone. Root
   `tf_providers.provider` tags are only for off-registry providers, and tags
   in dependencies are ignored. Every provider download must be gated on a
   SHA-256 digest: one of the lock file's `zh:` hashes, or the tag's `sha256`.
2. Building validates. `bazel build` on any `tf_library`, `tf_deploy` or
   `tf_test` target runs `tofu init -backend=false` and `tofu validate` (with
   the test directory for `tf_test`). Do not bypass or defer this. Every
   target, including libraries generated by `tf_modules`, must pass its checks
   before dependants run theirs. Manifest actions take direct dependencies'
   manifests as inputs, and validate actions take their stamps, plus the
   `var_files` check stamp on `tf_deploy`. Deploy launchers carry the deploy's
   stamps in default outputs and runfiles, and `tf_test` carries its validate
   stamp in runfiles.
3. Nothing under `tf/private/` is public API. Downstream modules load only
   `@rules_tofu//tf:defs.bzl`, `@rules_tofu//tf/providers:extensions.bzl`,
   `@rules_tofu//tf/modules:extensions.bzl`,
   `@rules_tofu//toolchain:extensions.bzl` and
   `@rules_tofu//toolchain:toolchain.bzl`. Every public `.bzl` entry point has
   a `starlark_doc_extract` target in `docs/BUILD.bazel`; add one for any new
   entry point.
4. Deploy launchers are ordinary executables. `tf_deploy`'s `.plan`, `.apply`
   and `.destroy` scripts find their runfiles tree and state directory relative
   to `$0`, so they work both under `bazel run` and when run directly. Neither
   the launchers nor the runner may read `BUILD_WORKSPACE_DIRECTORY` or the
   checkout; only `@tf_providers//:pin` writes to the checkout and requires
   `bazel run`. `tofu` runs in
   `<name>.rules_tofu-state/work/<pkg>`, never in runfiles or `<name>.work/`,
   and resolves `backend` blocks itself without runner rewrites.
   `@rules_tofu//tofu` is the only launcher that reads
   `BUILD_WORKING_DIRECTORY`. It changes to that directory only when the
   variable is set, so it also works under `bazel test` and in other tool runs
   where `BUILD_WORKING_DIRECTORY` is unset. It looks for the binary in
   `RUNFILES_DIR` and `TEST_SRCDIR` before `$0.runfiles`, because as a tool in
   another target's runfiles it has no runfiles tree of its own.

## Running the tests

```sh
# Go unit tests:
bazel test //tf/private/cmd/...

# Starlark unit tests (bazel_skylib unittest):
bazel test //toolchain/tests/... //tf/providers/tests/... //tf/modules/tests/... //tests/integration:versions_test

# Bazel-in-Bazel integration tests:
bazel test //tests/integration/...

# Integration tests on Bazel 8.5.0 (the supported floor). @running_bazel puts
# the nested builds on 8.5.0 too; restore MODULE.bazel.lock afterwards because
# 8.5.0 rewrites it in its own format:
USE_BAZEL_VERSION=8.5.0 bazel test //tests/integration/...
git checkout -- MODULE.bazel.lock

# `tofu test` targets (offline, network blocked):
bazel test //examples/hello/tests:all

# Real-module plans and the standalone BCR smoke module (excluded from //...
# via --deleted_packages in .bazelrc), as CI runs them:
bazel run //examples/modules/label:label.plan
bazel run //examples/modules/stack:stack.plan
bazel run //examples/modules/git:git.plan
(cd e2e/smoke && bazel build //... && bazel test //...)
```

On the pinned Bazel version, CI runs builds, tests and example plans with
`--lockfile_mode=error` and checks that `git status --porcelain` stays empty.

## Formatting and lint

No `bazel test` target checks formatting. CI's `lint` job runs
`bazel run //tools:format.check`, `bazel run //tools:lint` and
`bazel run //tofu -- fmt -check -diff -recursive examples e2e/smoke`, plus
`bazel mod tidy` to check that `MODULE.bazel` is unchanged. Run locally:

```sh
bazel run //tools:format
bazel run //tools:lint
bazel run //tofu -- fmt -recursive examples e2e/smoke
bazel mod tidy
```

`//tools:format` uses `rules_lint` to format git-tracked Go, Starlark, `.tf`
and `.tfvars` files, including `tests/integration` and nested workspaces. Set
`rules-lint-ignored` in `.gitattributes` to exclude a file. `rules_lint` 2.9.1
skips `.tofu`, `.tftest.hcl` and `.tofutest.hcl` files, so the `tofu fmt` step
is their only check. It names `examples` and `e2e/smoke` to skip
`tests/integration`, where negative-case fixtures may be malformed on purpose.

`//tools:lint` checks every Starlark file under the workspace, including nested
workspaces and untracked files, and fails on any formatting diff or buildifier
lint warning, such as missing `Args:` or `Returns:` doc-string sections. An
unformatted untracked Starlark file fails `//tools:lint` locally because
`//tools:format` formats git-tracked files only. Suppress a deliberate warning
in place with `# buildifier: disable=<warning>` and a reason.

When adding a nested Bazel module under `e2e/` or `tests/integration/`:

1. Copy the root `.bazelversion` into it. CI checks that every nested module has
   a `.bazelversion` byte-identical to the root file.
2. Add its four `bazel-*` symlinks (`bin`, `out`, `testlogs`, `<dir-name>`) to
   `.bazelignore`. CI checks all four entries exist.
3. Run `bazel run @rules_bazel_integration_test//tools:update_deleted_packages`
   to update `--deleted_packages` in `.bazelrc`.

Open PRs against `main` from a branch on a fork once the build, tests and lint
checks pass.

## Pinning OpenTofu releases

[`.github/workflows/tofu_versions.yml`](.github/workflows/tofu_versions.yml)
("Pin new OpenTofu releases") runs every Monday and pins any new stable OpenTofu
releases from the floor in [`toolchain/versions.bzl`](toolchain/versions.bzl)
upward, opening or updating one pull request on the `tofu-versions` branch. To
run it between schedules, trigger it via `workflow_dispatch` from the Actions
tab. Existing pins are kept indefinitely so workspaces pinning an older release
with `tofu.version` keep working.

The workflow authenticates with the `VERSIONS_PR_TOKEN` repository secret, a
fine-grained token scoped to this repository with read and write access to
Contents and Pull requests. If `VERSIONS_PR_TOKEN` is unset, it falls back to
`GITHUB_TOKEN`: the pull request still opens when "Allow GitHub Actions to
create and approve pull requests" is enabled in repository settings, but GitHub
does not trigger CI on pushes or pull requests made with `GITHUB_TOKEN`, so CI
must be started by hand, for example by closing and reopening the pull request.

To pin releases by hand, pass one or more `X.Y.Z` versions:

```sh
bazel run //tools:update_versions -- 1.12.13 1.13.10            # add to KNOWN_VERSIONS
bazel run //tools:update_versions -- --default 1.12.13 1.13.10  # also set DEFAULT_VERSION to the newest
```

`update_versions` requires `curl` on `PATH`. It downloads each release's
`SHA256SUMS`, verifies its Sigstore signature against the OpenTofu release
workflow identity using the `cosign` binary pinned in `MODULE.bazel`, and writes
the five platform digests into `toolchain/versions.bzl` once every signature has
verified, so a failure leaves the file unchanged. Do not paste digests in by
hand.

`tests/integration/BUILD.bazel` generates `module_dependency_<version>_test`
(dots replaced by underscores) for the floor and the newest patch of each minor
release (`tested_versions` in
[`tests/integration/versions.bzl`](tests/integration/versions.bzl)). To run one
of the non-default entries directly:

```sh
bazel test //tests/integration:module_dependency_1_12_12_test
```

With `--default`, the examples, `e2e/smoke` and the remaining integration tests
use the new version too.

`DEFAULT_VERSION` follows the newest stable release, including across minor
releases. Before merging a pull request that moves `DEFAULT_VERSION` to a new
minor release, check that minor release's OpenTofu changelog for changes to what
`rules_tofu` relies on: `tofu show -json -module`, the module manifest
(`.terraform/modules/modules.json`), the `.terraform/terraform.tfstate` backend
record, `tofu test -json-into`, `-plugin-dir`, `-get=false` and lock files.

## Go version floor

`tf_providers.from_lock` and `tf_modules.module` compile `lockjson` and
`modscan` with the downstream workspace's host Go SDK
(`tf/private/host_tools.bzl`). The `go` directive in `go.mod` is therefore a
floor for every consumer that registers a Go SDK, not only for this repository.
It cannot be lower than the pinned Go dependencies' own `go` directives
(`hcl/v2` sets it today), and Dependabot's `gomod` updates raise it with them.
Mention any increase in the release notes.

## Releasing

Releases are cut from SemVer tags (`vX.Y.Z`) and published to the
[Bazel Central Registry](https://registry.bazel.build/). Leave `version` unset
in `MODULE.bazel`, and keep comments out of `module(...)`: the tag is the sole
version source, and BCR patches the release version into the published
`MODULE.bazel`.

1. Tag the commit as `vX.Y.Z` and push the tag, or trigger
   [`.github/workflows/release.yaml`](.github/workflows/release.yaml) manually
   via `workflow_dispatch` for an existing tag.
2. `release.yaml` runs
   [`.github/workflows/release_prep.sh`](.github/workflows/release_prep.sh) to
   build `rules_tofu-vX.Y.Z.tar.gz` and `rules_tofu-vX.Y.Z.docs.tar.gz`. The
   docs archive comes from `bazel build //docs:all` and backs `docs_url` in
   `.bcr/source.template.json`. The workflow attaches build attestations and
   publishes the GitHub Release with a `bazel_dep` snippet.
3. Publish to the BCR:
   - Manual (required for a module's first submission): in a
     `bazelbuild/bazel-central-registry` clone, run
     `bazel run //tools:add_module` with the release tarball and
     [`.bcr/`](.bcr) templates, then open a PR.
   - Automated (opt-in): fork the BCR to `benbirt/bazel-central-registry`, add
     a classic `BCR_PUBLISH_TOKEN` secret (`repo` and `workflow` scopes), and
     set the repository variable `PUBLISH_TO_BCR=true`. The `publish` job then
     opens the BCR PR on each release.

Published BCR versions are immutable; to retract one, yank it via
`.bcr/metadata.template.json`.

`release_prep.sh` excludes `docs/`, which only feeds the docs archive, and
every package that references a `dev_dependency`: `examples/`, `tests/`,
`tools/`, `toolchain/tests/`, `tf/providers/tests/` and `tf/modules/tests/`.
It keeps `e2e/` and `.bcr/` for BCR presubmit.
